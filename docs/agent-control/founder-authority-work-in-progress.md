# bonUP founder and host-test authority runtime

Repository implementation only. This is not installation, service-start, host-test
execution, activation or Milestone-4 approval. No real founder signing key is
created, loaded or generated by production code. Generation 2 is not generated here.

## Historical and successor configuration

Generation 1 remains historical: its 60 tracked review files, candidate, inventory,
approval proposal and hashes remain unchanged. Its component version 2 and manifest
version 4 continue through their original validators. The generation-1 build helper
rehydrates historical payload bytes instead of silently packaging successor code.
Source: `tools/agent_control/installation_bundle.py:400` and
`tools/agent_control/installed_runtime.py:324`.

Successor component version 3 explicitly selects the separate closed contract in
`tools/agent_control/successor_config.py:41`. It requires installation generation 2,
a pinned founder root identity, Ed25519, the fixed verification dependency, exact
purposes, explicit feature booleans, catalog version/digest, durable audit and
receipt requirements, interruption policy and activation=false. Unknown fields,
legacy identity injection, missing dependencies and ordinary execution catalogs are
rejected. Enabling host tests requires founder enrollment to be enabled.

The future root-controlled `/etc/bonup-agent-control/runtime-authority.json` is a
post-install runtime attestation, not the historical candidate and not a replacement
for an approved installation manifest. It binds configuration digests, exact runtime
file hashes, the installed receipt digest and physical root-enrollment digest. Its
candidate/approved identities refer to separately retained installation records;
there is no attempt to include a receipt's future digest inside its own candidate.
The loader verifies the closed approval projection and equality of the approved
file/configuration/resource/identity policies before operational enrollment.
Source: `tools/agent_control/installed_runtime.py:392`.

Future Generation-2 packaging and provisioning must separately inventory the static
component/public-trust policy and define creation of these post-install records:
`runtime-authority.json`, `authority-receipt.json`, `host-test-roots.json`,
`installation-candidate.json` and `installation-approved.json`, all under the fixed
root-controlled configuration directory. Runtime attestation is not self-approval:
installation and integration-service permission must already be explicitly recorded.
No function here manufactures that permission. The founder signature is still
required for installation decisions and, separately, host-test admission.

## Founder trust and verification

The separately reviewed `/etc/bonup-agent-control/founder-root.json` holds only the
public Ed25519 key, key ID, trust generation and permitted purposes. Installed
policy pins its digest. Transport requests cannot choose or replace this key.
`/usr/bin/openssl` is the owner's approved OS dependency; no package is installed.
The verifier pins the root-controlled executable, uses argv without a shell, a
minimal environment, sealed memfd inputs, bounded output and a two-second timeout.
Compatibility is OpenSSL 3.x (minimum 3.0), with public RFC 8032 positive and negative
verification probes, permitting compatible patch updates.
Source: `tools/agent_control/founder_crypto.py:41`, `:62` and `:142`.

The founder signs canonical challenges outside the VPS. Challenges bind observed
UID/GID/PID/start/boot, nonce, enrollment generation, exact candidate/installation
identities, key identity, purpose and expiry. The monotonic ceiling is captured
before audit work, so slow audit cannot extend it. Sessions are consumed once,
process-bound and purpose-bound; boot/process/enrollment changes invalidate them.
Installation signatures cannot authorize host testing. Activation purpose is
unsupported. Root invocation, UID 1000 and unsigned JSON create no founder session
within the verified runtime and trust policy.
Source: `tools/agent_control/founder_session.py:22`.

## Admission, catalog and normal execution

Both services begin admission-closed and reconcile before accepting the separate
signed host-test authorization. The controller additionally verifies the exact
receipt. HOST_TEST_ONLY permits only the 18 immutable catalog IDs. The catalog fixes
worker identity, payload, roots and resource profile. There is no caller executable,
argv, path, environment, capability or resource override. Ordinary proposals and
ordinary admission remain disabled in the successor runtime, including when host
tests are disabled. Session end returns CLOSED.
Source: `tools/agent_control/host_test_catalog.py`,
`tools/agent_control/host_test_runtime.py:18`, and
`tools/agent_control/operational_enrollment.py`.

Catalog grants, preparation, final authority recheck, pinned confinement, release
and exec-start confirmation use the normal controller/supervisor path. The host
route does not introduce a privileged supervisor execution bypass. Audit receipt,
authorization and denial use one request correlation; authorization is emitted
only after normal authority validation succeeds. Setup/start/exit use that same
request ID, with the allocated launch ID added afterward. Session, test and receipt
correlation accompanies durable host-test evidence. Audit failures prevent further
execution and are not mislabeled as failed authority validation.
Source: `tools/agent_control/host_test_launch.py:129` and
`tools/agent_control/host_test_runtime.py:80`.

## Interruption and reboot evidence

The interruption canary waits inside normal confinement until interruption or its
unchanged execution deadline. Arming requires confirmed RUNNING evidence and pins
launch/process/target/cgroup identities. It persists pending state and closes future
admission without stopping the canary. It invalidates the founder session.
Source: `tools/agent_control/host_test_runtime.py:142`.

The surviving trusted component uses pidfds to observe target death while the exact
canary remains live; stopped, exited or unobservable canaries are rejected. It
checks cgroup identity before normal cleanup, then persists bounded evidence after
cleanup. Slow or failed evidence storage cannot delay launch termination.
Controller-loss observations are owned by the supervisor; supervisor-loss
observations are owned by the controller. No supervisor SQLite writer is introduced.
Source: `tools/agent_control/interruption.py:36` and the disconnect hooks in
`tools/agent_control/composition.py` and `tools/agent_control/installed_runtime.py`.

Generation-2 provisioning must separately create these fixed evidence directories:

| Path | Owner/group | Proposed mode | Lifecycle |
|---|---|---|---|
| `/var/lib/bonup-agent-control/runtime/interruption` | 3000:3000 | 0700 | Persistent investigation evidence |
| `/var/lib/bonup-agent-supervisor` | root:root | 0755 | Persistent root-owned evidence parent |
| `/var/lib/bonup-agent-supervisor/evidence` | root:root | 0755 | Persistent root-owned observations |

Files have exact UUID names and mode 0644, contain bounded identity/observation data
and are never worker mounts. Runtime validates existing directory ownership and
non-writability by other identities; it does not create these directories. Preserve
these records during rollback/investigation. No directory was created by this task.

Reconciliation requires fresh signed authority, fresh operational enrollment,
required generation/boot changes, the exact persisted kernel witness and verified
whole-launch cleanup. Service crash/watchdog cases additionally require a fresh
bounded systemd event and a completed post-restart canary through normal confinement.
The only extra read-only OS command is fixed `/usr/bin/journalctl`, restricted to the
two agent-control units. A journal message alone, pre-stopped worker, ambiguous
simultaneous death, uncertain descendants or missing witness cannot produce PASS.
Reboot does not resume workers or reusable authority.
Source: `tools/agent_control/host_test_runtime.py:163` and
`tools/agent_control/service_evidence.py`.

Completion checks every mandatory test, catalog version, worker, unique launch,
receipt/installation identity, runtime evidence context and PASS result. Completion
is evidence only and does not open admission or activate agents.
Source: `tools/agent_control/host_test_runtime.py:121`.

## Corrective host-test authority closure

The follow-up correction adds protocol version 4 only for bounded host-test
admission operations. OPEN and CLOSE bind the installed identity digest, the
operational enrollment digest (which binds both enrolled participants and their
generations), and the signed host-test delegation digest. The normal authenticated
controller channel is the sole caller; no founder/model/worker direct operation
exists. Legacy OPEN cannot enable successor host-test admission.

END and successful COMPLETE first close local admission and consume the delegation,
then require matching supervisor closure and cleanup evidence. The supervisor closes
before cleanup, retains the consumed session identity, and cannot reopen it even
with a fresh request ID. Only observation/rechecking of closure is idempotent.
Completion is finalized in the existing durable audit/metadata path after closure;
its retained results are evidence and cannot be used as a session. Subsequent END,
COMPLETE, enrollment, run, or evidence-recording requests under that session fail.

Lost/malformed/stale closure acknowledgement, audit failure or uncertain cleanup
invalidates the operational channel and stops heartbeats. Controller admission stays
CLOSED; the supervisor's existing disconnect/deadline enforcement handles loss.
No completion/end success is reported. Fresh operational enrollment/reconciliation
and separately signed authority are required for later host testing. No release is
retried. Expiry, receipt replacement, fatal request failure, revocation and shutdown
use the same closure boundary. Revocation invalidates retained verifiers before audit
I/O, and shutdown closes the operational channel even if founder teardown fails.

An explicit INTERRUPTION closure is the only keep-running case: both sides close
new admission/release, but the supervisor preserves exactly one already RUNNING,
exec-confirmed closed-catalog interruption canary under its unchanged deadline.
It returns closed admission with cleanup still false; this cannot finalize END or
COMPLETE. The existing pending-interruption/reconciliation path must prove cleanup.

Correlated audit events record closure request, supervisor confirmation or
uncertainty, authority consumption, session end and final completion. No new audit
store or installation authority is introduced. Generation 1 remains unchanged.

Corrective validation: 29 closure tests, 52 founder tests, 30 service-runtime tests,
and the installed successor factory check passed. The full agent-control suite
passed all 707 tests in 516.578 seconds. Compile/import and whitespace checks
passed; the 76 captured source/schema hashes were unchanged during that full run.
All 60 tracked Generation-1 historical review files remain unchanged.
