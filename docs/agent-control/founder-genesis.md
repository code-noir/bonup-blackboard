# bonUP offline Founder Genesis contract

Repository model only. No ceremony, key generation, installation, service start,
host test or activation is authorized by this document or by generated records.

## Trust anchor and human boundary

The human Founder's deliberate offline Genesis ceremony is the initial trust
anchor. It is not authorized by another key. A signature by the proposed key
proves possession, not authority to select that key. VPS root, sudo, UID 1000,
SSH, JSON and program invocation are not ceremony confirmation.

`founder_genesis.OfflineCeremony` is the strict adapter boundary. Its production
default raises an authority error. There is no command-line, stdin, unattended
confirmation, `--yes`, `--force`, auto-signing or runtime RPC implementation.
The future offline UI must be independently reviewed before real use. Synthetic
adapters exist only in tests. Supplying arbitrary Python callbacks is not an
untrusted-user API: these are trusted composition inputs, like existing kernel
observation adapters. No production factory selects an adapter from request data.

The UI must show every canonical challenge field and require the Founder to
independently compare source commit, candidate digest, bundle digest, installation
generation, root-policy digest, Ed25519 fingerprint and root generation. The full
SHA-256 challenge digest is authoritative. Its first 16 hexadecimal characters
are only a comparison aid. Deliberate confirmation returns the full digest; a
short code, boolean or caller-supplied JSON is insufficient. Challenges last five
minutes, bounded independently by monotonic time so wall-clock rollback cannot
renew them. Signing keys remain external. No real key is generated by this module.

## Durable one-time consumption

The authoritative trust-domain ledger belongs to the offline ceremony, outside
VPS control. It must be preserved across process restart, reboot and reinstall.
`GenesisLedger` operates on an already established private SQLite connection.
It never creates a database/table or a missing domain row. Missing, corrupt,
non-virgin or previously consumed state fails closed.

Future offline initialization must deliberately establish exactly one VIRGIN
domain only after independently excluding previous root generations, bindings
and installation receipts. That operation is not implemented or authorized here.
The ledger must not be placed under a VPS-controlled path, reset from a stale
backup, or reinitialized when a caller loses its binding. Such recovery would
destroy the trust anchor and is outside this protocol. Root on a compromised VPS
cannot be prevented from replacing all local code; it cannot obtain an authorized
second ceremony from the independent offline ledger through this interface.

The compare-and-set transaction commits CONSUMED and the complete binding before
publishing a successful result or emitting final audit events. A later failure
does not restore VIRGIN. Competing confirmations cannot both consume. Lost output
requires recovery of existing evidence; never a second Genesis. Rotation is
unsupported. No generation greater than one can be requested for the root.

## Candidate, binding and approval

The candidate contains the closed `founder_root_policy` and no actual public key.
The future Generation-2 generator must supply its strict complete-manifest
validator to `candidate_identity`; there is no permissive default or trusted
`complete=true` field. Eligible candidates are `COMPLETE_BUT_ROOT_UNBOUND`.

Genesis produces a separate immutable binding and moves the model to
`ROOT_BOUND_BUT_UNAPPROVED`. Candidate bytes/digest never change. The binding
contains canonical base64 of exactly 32 public bytes, SHA-256-derived key ID,
root generation one, candidate identities, policy digest, canonical challenge,
ceremony UUID and binding digest. It remains approved=false and activation=false.

The binding stage permits exactly one new field in the bound installation
representation: `founder_root_binding_digest`. The subsequent approval projection
changes only approved and the derived bundle digest. No other candidate policy
or artifact can change. `PROPOSED_APPROVAL_STAGE` is review data, not approval.
An installation-purpose challenge signed externally by the exact bound root is
still required. The existing founder intake emits `APPROVED_FOR_INSTALLATION`
only after signature/session validation, exact projection validation and audit.
Host testing requires its own receipt-bound purpose. Activation remains disabled.

## Installed representation and receipts

Successor component version 4 uses authority-policy version 2 with the key-free
root policy. Version 3 remains a historical synthetic fixture contract and is
rejected by the production KernelIO loader. Generation-1 component version 2 and
historical files retain their original behavior.

Future exact public artifacts under `/etc/bonup-agent-control` are:

| Artifact | Owner/group | Mode | Contents |
| --- | --- | --- | --- |
| `founder-root.json` | root:root | 0444 | Canonical public key, derived ID, algorithm, generation, purposes |
| `founder-root-binding.json` | root:root | 0444 | Complete offline binding |
| `founder-genesis-evidence.json` | root:root | 0444 | Version 1, state GENESIS_ALREADY_PERFORMED, binding_digest |

The directory must be root:root 0755. No symlink, founder/controller/worker write
access or runtime replacement is permitted. The existing descriptor-relative
installed readers enforce root control and reject symlinks and unsafe modes.
Installation must verify canonical bytes and hashes; permissions never substitute
for matching the approved identity. No private-key file is accepted.

Runtime checks match candidate/bundle/generation/policy, binding digest, canonical
key ID, root generation, installed root and receipt projection before operational
enrollment. Approval and founder challenges carry the binding digest as part of
the installation identity. Receipt version 2 retains challenge digest, root
binding/policy digests, key ID, root generation and canonical public-artifact hash.
It also retains candidate, bundle and approved manifest/inventory identities.
Receipt evidence cannot authorize execution or activation.

Before any later installation mutation, preflight must validate all these exact
identities, canonical public-key encoding and artifact hashes, destination
conflicts, and the fixed OpenSSL 3.x positive/negative Ed25519 verification probe.
No host check is performed by this module. Offline ledger and Genesis evidence
must be retained in history and excluded from destructive rollback.

## Corrective Ed25519 public-key validation

Founder keys must pass system libsodium's
`crypto_core_ed25519_is_valid_point()` before an authoritative fingerprint is
derived. This positive predicate checks canonical representation, curve and main
subgroup membership, and excludes small-order points. The previous two-encoding
rejection rule was insufficient: the reviewed order-two fixture passed it and
OpenSSL 3.0.13 accepted a constructed signature with no private-key operation.
OpenSSL `pkey -pubcheck` is not a substitute. No handwritten curve arithmetic or
blacklist is used by the correction.

The dependency is system `libsodium23`, ABI/SONAME `libsodium.so.23`, under the
fixed `/usr/lib/x86_64-linux-gnu` directory. Read-only inspection found package
`1.0.18-1ubuntu0.24.04.1`, resolved library `libsodium.so.23.3.0`, runtime version
1.0.18, and both required symbols. No package was installed or changed.

The native adapter takes exactly 32 bytes. It verifies root-controlled directories,
SONAME link and regular library, restricts the link to the same ABI's versioned
basename, and loads a retained pinned descriptor using ctypes RTLD_LOCAL/NOW.
The descriptor and handle remain paired for process life, avoiding descriptor-name
reuse with the dynamic loader cache. Root-controlled compatible patch updates are
picked up on process restart. There is no library search, caller-selected path,
symbol, algorithm, signing API, PyNaCl or native-provider fallback. Native-loader
environment overrides are rejected. The two signatures are fixed: sodium_init
takes no arguments and returns int; the valid-point function takes a 32-byte
unsigned-byte buffer and returns int. Init must return 0 or 1. Only predicate
result 1 accepts a key; dependency errors latch failure until process restart.

Future Generation-2 preflight must verify this ABI/path, both symbols, successful
sodium_init, acceptance of the public RFC 8032 vector, and rejection of the exact
reviewed order-two fixture. Feature probes, rather than a patch-version equality,
define compatibility. The successor policy digest includes this dependency.
The binary is an OS dependency, not copied into a bundle.

Validation is repeated at Genesis entry, FounderRoot construction, installed
public-artifact parsing, session construction and before OpenSSL signature
verification. Installed parsing additionally requires the derived key ID and
canonical algorithm/generation/purpose fields; successor startup retains the
candidate, binding and receipt checks. Invalid Genesis attempts emit the bounded
INVALID_FOUNDER_ROOT_KEY reason and do not consume the ledger. A valid attempt
afterward can still consume it exactly once. OpenSSL remains responsible only
for Ed25519 signature verification; external hardware retains the private key.

## Audit and validation

The offline adapter supplies a durable bounded audit sink for proposal, malformed
key/candidate denial, confirmation, binding creation and duplicate denial. Events
contain digests, never signing material. Consumption is independently committed
even if a final audit callback fails. Installed installation/host-test decisions
continue through the controller's existing audit/outbox.

Tests use public synthetic vectors, a synthetic human adapter, private temporary
SQLite state and the existing test-only signer. Real offline UI, ledger custody,
hardware fingerprint comparison, installation and host enforcement remain future
review/host-test obligations. This contract does not generate Generation 2.
