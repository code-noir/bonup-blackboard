Today’s Build Summary

Today was a major backend contract-management day. You moved beyond isolated engine logic and turned several core lifecycle concepts into real contract-side workflow, persistence, proof output, and API surface.

The biggest thing that happened today is this:

You did not just “add features.”
You connected the engine to the contract system in a way that makes the app behave more like a real contracting platform.

What was built today

1. Stored value adjustments became real contract data

Before, value adjustments were mostly something the engine or proof could derive.

Today, you made them persistent contract-side records.

That means Blackboard can now store financial outcomes like:
	•	lateness adjustment
	•	additional charge

instead of only generating them on the fly.

What was added
	•	ContractValueAdjustment model
	•	value adjustment repository
	•	value adjustment service
	•	persistence tests
	•	proof now reads stored adjustments instead of relying only on event metadata

Why this matters

This is important because now:
	•	adjustments are auditable
	•	proof can show real stored business records
	•	contract management can use them
	•	later billing can use them

This is one of the biggest moves from “engine experiment” to “platform behavior.”

⸻

2. Proof of work got upgraded into a stronger management-proof object

Your ProofOfWorkService became much richer.

Originally, proof mainly showed:
	•	execution sessions
	•	events
	•	observations
	•	decisions

Now proof can also show:
	•	stored value adjustments
	•	approval requests
	•	promotion records
	•	promoted side obligations
	•	contract mode

What was connected into proof

For service obligations, proof now includes:
	•	approval_requests
	•	promotions
	•	promoted_side_obligations
	•	value_adjustments
	•	contract_mode

For payment obligations, proof includes:
	•	contract mode
	•	stored value adjustments
	•	approvals where relevant

Why this matters

Proof is now getting close to a real operational evidence document.
It is no longer just “events that happened.”
It is becoming:
	•	evidence
	•	decisions
	•	approval history
	•	financial outcomes
	•	promotion outcomes

That is exactly the kind of payload that later powers:
	•	PBVD
	•	contract management UI
	•	exports
	•	audits

3. Execution workflow became a real API workflow

You exposed the execution system through API.

This was a major block of work.

Execution endpoints built
	1.	POST /api/contracts/obligations/<obligation_type>/<obligation_id>/execution-sessions/
	2.	GET /api/contracts/obligations/<obligation_type>/<obligation_id>/execution-sessions/
	3.	POST /api/contracts/execution-sessions/<session_id>/execution-items/
	4.	GET /api/contracts/execution-sessions/<session_id>/events/
	5.	POST /api/contracts/execution-sessions/<session_id>/close/

What these do

They allow the app to:
	•	open an execution session under an obligation
	•	list sessions
	•	record execution items
	•	list execution events
	•	close a session

What happens when recording an execution item

When an execution item is recorded:
	•	the engine evaluates it
	•	a decision is returned
	•	the event is stored
	•	metadata contains:
	•	decision status
	•	authorization mode
	•	billing mode
	•	promotion suggestion
	•	required next step
	•	rationale
	•	proof tags

Why this matters

This is the API layer that turns the execution engine into something the UI can actually use.

Without this, execution was mostly internal logic.
With this, it is now a product workflow.

⸻

4. Approval workflow was created and exposed through API

This was another huge step.

You built a real approval domain for out-of-scope or conditional work.

Approval model and backend pieces
	•	ContractApprovalRequest model
	•	approval repository
	•	approval service
	•	approval API views
	•	approval serializers

Approval endpoints built
	1.	POST /api/contracts/obligations/<obligation_type>/<obligation_id>/approval-requests/
	2.	GET /api/contracts/obligations/<obligation_type>/<obligation_id>/approval-requests/
	3.	POST /api/contracts/approval-requests/<approval_id>/approve/
	4.	POST /api/contracts/approval-requests/<approval_id>/reject/

What this means in business terms

This is where a client or homeowner can approve or reject a task that was detected during execution but was not part of the original scope.

Example:
	•	mowing is the original service
	•	branches are found on site
	•	branch removal is not clearly in scope
	•	contractor records the item
	•	engine says approval_required
	•	approval request is created
	•	homeowner approves or rejects the work

Why this matters

This creates a real trail for:
	•	who requested something
	•	what was being approved
	•	whether it was approved or rejected
	•	when it was decided

This is major for trust, disputes, proof, and management view.

⸻

5. Automatic approval creation was added

At first, approval request creation was manual.

You changed that.

Now when an execution item is recorded and the engine returns:
	•	decision_status = approval_required

the system automatically creates an approval request.

Resulting flow

Now the flow is:
	1.	contractor records execution item
	2.	engine evaluates it
	3.	event is stored
	4.	approval request is auto-created if approval is required

Why this matters

This closes a major workflow gap.

Before:
	•	engine said approval was needed
	•	but the app still needed a second separate call to create the approval record

Now:
	•	the request is opened automatically
	•	users do not have to remember the extra step

That makes the conditional workflow much more trustworthy.

⸻

6. Automatic additional charge creation after approval was added

You connected approval decisions to stored value adjustments.

Now when an approval is approved, and the approval metadata indicates:
	•	billing_mode = separate_charge

the system automatically creates a stored additional_charge.

What was built
	•	approval approval flow now triggers value adjustment service
	•	additional charge gets stored automatically
	•	duplicate prevention was later added

Why this matters

This means approved out-of-scope work can now produce a real financial consequence automatically.

This is one of the strongest contract-management flows you built today.

⸻

7. Duplicate additional charge bug was fixed

When auto-charge was added, the same approval could create duplicate additional_charge records if approved again.

You fixed that.

What was added
	•	repository method to find existing additional charge by execution event
	•	idempotent guard in approval service

Meaning

Now:
	•	one execution event
	•	one approval
	•	one resulting additional charge maximum

Why this matters

This is a backend quality step.
Not flashy, but important.
It prevents silent financial duplication.

⸻

8. Side-obligation promotion flow was built

This was another major milestone.

You created the ability to promote an execution event into a new side service obligation.

What was added
	•	ContractObligationPromotion model
	•	promotion repository
	•	promotion service

What the promotion does

It takes an execution event and creates:
	•	a promotion record
	•	a new side ContractServiceObligation
	•	a link from the original service obligation to the promoted one

Business meaning

Example:
	•	contractor is mowing
	•	branches are detected
	•	branch removal is too large to remain just an event
	•	it gets promoted into its own service obligation

Why this matters

This is how the system turns discovered work into structured contract work.

That is a very strong concept.

⸻

Promotion was originally shell-only.

You exposed it through API.

Promotion endpoint built

POST /api/contracts/execution-events/<execution_event_id>/promote/

What it returns
	•	promotion record
	•	promoted service obligation summary

Why this matters

Now promotion is not just a backend service.
It is a UI-usable workflow.

10. Automatic promotion after approval was added

After approval was approved, if the approval metadata indicated:
	•	promotion_suggestion = suggest_side_obligation

the system automatically promoted the execution event into a side service obligation.

Final connected flow

Now the fresh-case workflow can do this:
	1.	open session
	2.	record execution item
	3.	auto-create approval request
	4.	approve approval request
	5.	auto-create additional charge
	6.	auto-promote to side obligation

Why this matters

This is one of the strongest backend flows you’ve built so far.

It means Blackboard can now:
	•	detect out-of-scope work
	•	request approval
	•	record financial impact
	•	structure the work into a separate obligation

That is serious contract-execution logic.
